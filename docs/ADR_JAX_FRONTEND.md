# ADR 0001: JAX Frontend Architecture and Jaxpr Intermediate Representation Boundary

- **Status**: Accepted
- **Deciders**: Python-HLS Engineering
- **Date**: 2026-09-10
- **Issue**: [DragonX-Systems/python-hls#1](https://github.com/DragonX-Systems/python-hls/issues/1)

---

## 1. Context and Problem Statement

Modern scientific computing, machine learning, and algorithmic trading models are frequently written in [JAX](https://github.com/google/jax). JAX provides a functional, composable API based on NumPy primitives, automatic differentiation (`grad`), hardware vectorization (`vmap`), and just-in-time compilation (`jit`).

When moving from Python-based model research to specialized FPGA or ASIC accelerators, engineering teams often have to manually re-implement JAX models in C++ or SystemC for High-Level Synthesis (HLS). This creates a dual-model problem: numerical discrepancies, precision drift, and latency disconnects between the Python reference and the synthesized RTL.

**Goal**: Evaluate and establish an inspectable JAX frontend in Python-HLS for statically shaped kernels, preserving visibility into scheduling, resource allocation, and generated hardware netlists without requiring a separate C++ translation.

---

## 2. Considered Alternatives

We evaluated three potential staging boundaries for ingesting JAX kernels into Python-HLS:

### Option 1: Jaxpr (`jax.core.Jaxpr`) [CHOSEN]

A **Jaxpr** (JAX expression) is JAX's internal, typed, functional single-static-assignment (SSA) intermediate representation. It is generated by staging a Python function through JAX's abstract interpreter (`jax.make_jaxpr(fun)(*example_args)`).

- **Structure**:
  - `invars`: Typed input variables with concrete `core.ShapedArray(shape, dtype)`.
  - `constvars`: Typed compile-time constants.
  - `eqns`: Linear sequence of primitive equations (`JaxprEqn`) referencing atomic primitives (e.g., `add_p`, `mul_p`, `dot_general_p`, `reduce_sum_p`).
  - `outvars`: Typed output variables.
- **Advantages**:
  - **Zero Heavy C++ Dependencies**: Jaxpr is a pure Python data structure native to `jax.core`. It requires no MLIR/LLVM toolchain or C++ compilers to construct, inspect, or traverse.
  - **Fully Materialized Type System**: Abstract evaluation resolves all broadcasted shapes, canonical data types, and dimension numbers prior to ingestion.
  - **1-to-1 Mapping to Hardware Dataflow**: Functional SSA equations map directly to Python-HLS dataflow graphs (`IRFunction`, `IRBlock`, `IROperation`, `IRVariable`), enabling direct ASAP, ALAP, and List scheduling.
  - **Inspectability**: Clean, human-readable graph representation that can be visualized and analyzed for latency, area, and power tradeoffs.
- **Disadvantages**:
  - Internal to JAX (though foundational and exceptionally stable across JAX releases).
  - Dynamic runtime control flow requires structured higher-order primitives (`cond_p`, `while_p`, `scan_p`).

### Option 2: StableHLO (MLIR Bytecode / Textual Dialect)

[StableHLO](https://github.com/openxla/stablehlo) is an operation set designed for portable machine learning computation, exposed via MLIR. JAX can export to StableHLO via `jax.export.export(fun)(*args).mlir_module()`.

- **Advantages**:
  - Formal multi-vendor specification with backward compatibility guarantees across XLA targets.
- **Disadvantages**:
  - Requires heavy C++ MLIR Python bindings or complex text parsing of multi-dialect MLIR (`chlo`, `stablehlo`, `func`, `builtin`).
  - Disproportionately heavy dependency footprint for an agile, Python-first HLS compiler.
  - Opaque serialization makes early inspectability and rapid design-space exploration (DSE) more cumbersome.

### Option 3: AST-Level Duck Typing / Interception

Intercepting `jax.numpy` calls via AST manipulation or monkey-patching similar to standard Python AST parsing.

- **Advantages**:
  - Minimal dependency footprint.
- **Disadvantages**:
  - Bypasses JAX's abstract interpreter, transformation pipeline (`vmap`, `jit`), and staging semantics.
  - Fails to capture functional compositions or JAX-specific optimizations.

---

## 3. Decision Outcome

**Chosen Decision**: **Import and lower through JAX Tracing / Jaxpr (`jax.core.Jaxpr`)**.

### Rationale

1. **Direct Hardware Alignment**: A Jaxpr equation is an SSA operation between typed value buffers. This aligns precisely with Python-HLS's Intermediate Representation (`IROperation(op_type, operands, result)`).
2. **Deterministic Shape & Dtype Materialization**: JAX's abstract interpretation resolves shapes and types upstream, eliminating ambiguity before hardware scheduling.
3. **Pure Functional Semantics**: Jaxpr functions are guaranteed side-effect free and referentially transparent, perfectly satisfying Python-HLS's strict semantic rules.
4. **Lightweight & Inspectable**: Jaxpr allows users to inspect the operation schedule and hardware allocation directly in Python without installing LLVM or MLIR toolchains.
5. **Future Interoperability**: Since JAX lowers Jaxpr to StableHLO internally, supporting Jaxpr establishes the necessary primitive mapping should a future StableHLO bytecode reader be added.

## 4. Architectural Constraints & Boundaries

To ensure physical synthesizability, the JAX frontend enforces the following constraints:

### 1. Static Shapes
- All tensor and array operands must have **statically known, positive integer shapes** (e.g., `(16,)`, `(4, 4)`).
- Variable-length dimensions, dynamic shapes (`None`, `-1`), or data-dependent slice bounds are strictly prohibited and rejected deterministically with `JAXShapeError`.

### 2. Canonical Hardware Data Types
All arrays must normalize to supported physical bit widths:
- Signed Integers: `int8` (8-bit), `int16` (16-bit), `int32` (32-bit), `int64` (64-bit)
- Unsigned Integers: `uint8`, `uint16`, `uint32`, `uint64`
- Floating Point: `float32` (IEEE single-precision), `float64` (IEEE double-precision)
- Booleans: `bool` (1-bit)
- Complex numbers, strings, and arbitrary Python objects are rejected with `JAXDTypeError`.

### 3. Pure Functional Semantics & Zero Side Effects
- Kernels must not read or mutate module-level global variables.
- Kernels must not invoke I/O (`print`, file reads, network calls).
- This is naturally enforced by JAX's tracing environment and verified by Python-HLS semantic checks.

### 4. Bounded Control Flow
- Loops within kernels must be statically bounded and unrollable or lowerable to hardware finite state machine (FSM) control loops.
- Unbounded while-loops or unbounded recursion are rejected.

## 5. Relationship to Other Frontends

Python-HLS now defines three distinct frontend ingestion pathways:

| Frontend | Source Representation | Ingestion Mechanism | Primary Target Audience | Hardware Abstraction |
|---|---|---|---|---|
| **Bounded NumPy** (`python_hls/frontend/numpy`) | Python source code / AST with `import numpy as np` | AST desugaring to bounded loop nests and scratchpad allocations | Algorithmic trading, signal processing, explicit loop architectures | Explicit nested loops (`ast.For`), memory indexing (`LOAD`/`STORE`), scratchpads |
| **PyTorch FX** (`python_hls/frontend/torch_fx`) | `torch.nn.Module` | Symbolic tracing via `torch.fx` into `TorchFXGraph` | PyTorch neural network inference and ML accelerator prototyping | Module graph exploration, tensor metadata, coarse-grained layer analysis |
| **JAX / Jaxpr** (`python_hls/frontend/jax`) | JAX callable / function | Abstract interpretation tracing into `JaxprGraph` and `IRFunction` | Functional ML, differentiable pipelines, scientific computing, tensor linear algebra | Fine-grained functional SSA primitives mapped directly to scheduled IR functional units |

## 6. Qualified Prototype Primitive Mapping

The initial qualified JAX frontend prototype supports the following primitives:

| JAX Primitive | Python-HLS Mapping | Hardware Realization |
|---|---|---|
| `add_p` | `OperationType.ADD` | Pipelined adder functional unit |
| `sub_p` | `OperationType.SUB` | Pipelined subtractor functional unit |
| `mul_p` | `OperationType.MUL` | Hardware multiplier / DSP block |
| `div_p` / `integer_pow_p` | `OperationType.DIV` / `POW` | Pipelined divider / power unit |
| `neg_p` | `OperationType.NEG` | Two's complement negate unit |
| `abs_p` | Comparator + Negate | Hardware absolute value unit |
| `dot_general_p` | Nested MAC loops | Matrix multiplier datapath with scratchpad accumulator |
| `reduce_sum_p` | Accumulator tree / loop | Adder reduction tree |
| `max_p` / `min_p` | `OperationType.GT` / `LT` + MUX | Hardware multiplexer comparator (e.g. ReLU) |
| `clamp_p` | Dual comparator + MUX | Hardware window clipper |
| `transpose_p` | Memory address generator | Index permutation in scratchpad RAM |
| `reshape_p` | Memory stride recalculation | Zero-cost logical stride remapping |
| `broadcast_in_dim_p` | Replicated memory loads | Static broadcast address generator |

---

## 7. Limitations & Future Roadmap

1. **Higher-Order Control Flow**: Future work will expand support for `jax.lax.scan` and `jax.lax.cond` into multi-block hardware state machines.
2. **Quantization Annotations**: Adding support for custom fixed-point quantization schemes within Jaxpr tracing (e.g., `qint8`, `qint16`).
3. **StableHLO Exporter**: Providing an export bridge from Python-HLS IR back to StableHLO for downstream verification with OpenXLA.
